# 当前回合联合规划研究方案

这个方案针对两个相互耦合的决策：单位在网格上的动作序列，以及本回合最多十个市场订单的顺序。它是研究和验证方案，不是已授权的线上提交方案。

## 先固定官方语义

每个 callback 的决策输入是 `observation[t]`，执行的是 `steps[t+1].action`。单位动作先执行；随后市场按订单索引逐槽处理：HIRE、BUY_LAND 先以原子操作结算，SELL、BUY_PRODUCT、BUY_SEED、BUY_ANIMAL 再逐单位报价和成交。每个槽位两边先同时报价，再按座位提交；成功交易会立即改变市场库存和下一单位价格。BUY_PRODUCT 在库存减一的位置报价，SELL 在当前库存报价。

因此订单顺序影响三件事：价格、现金能否支付后续投资、对手在同一索引上的竞争。固定把所有 SELL 放前面是一个可解释的默认值，但不是全局最优规则。

## 状态、任务和目标

### 市场状态

规划器应读取：

- 我方现金、种子、每个单位库存、仓库库存和剩余容量；
- 市场库存与当前价格参数；
- 当前市场订单的操作、商品和数量；
- 当前回合单位动作执行后会产生或消耗的物品；
- 当天已雇工数、土地和动物购买的资金约束。

对手的私有仓库不可见，不能假设精确数量。只能使用公开的农场地块、动物和历史公开行为构造压力情景。

### 网格任务

把未来有限窗口内的动作抽象成带约束的任务：HARVEST、WATER、FEED、FERTILIZE、COLLECT_FERTILIZER、PICKUP、DROP/PLACE、PLANT 和 BUILD。每个任务有位置、最早开始时间、截止时间、预计产量增量、所需输入、占用回合数和失败后果。

任务价值使用保守的市场价格估计，并扣除走路、输入、雇工和容量风险。相同作物的多个任务不能只按距离排序，因为浇水窗口、成熟时间、同一仓库的空间和返程会改变总收益。

## 两层有限搜索

### 第一层：单位任务分配和路线

1. 以父模型本回合和未来短窗口的动作作为 baseline。
2. 为每个单位生成有限候选：继续原路线、完成一个高价值任务后回仓、完成两个可串联任务后回仓，以及只修复一个即将过期的任务。
3. 使用 Manhattan 距离生成可执行路径，但用 beam 或小规模 branch-and-bound 按“总产出价值 − 走路成本 − 返程/容量风险”排序；任务由所有单位共享，分配后从候选集中删除，避免两个单位争同一块地。
4. 用抽取的官方单位内核逐步模拟候选，检查成熟、浇水窗口、农产品增量、回仓时间和夜间容量。候选必须满足：不丢 baseline 已确认的收获、无新增溢出、不能让已有的输入/雇工承诺失效。

先只允许替换一个单位、一个短窗口，确认安全后再增加第二个单位。这样可以把“全局匹配”限制在可审计的局部范围，避免一次改动牵动整条路线。

### 第二层：市场订单排序

对第一层候选产生的 post-unit 仓库状态，枚举原订单的有限排列：

- 订单数不超过 6 时枚举去重后的全部排列；
- 订单数更多时，只尝试单订单跨槽移动、相邻交换和父排序；
- 不默认删除订单，不改变数量，不增加 HIRE/BUY_ANIMAL/BUY_PRODUCT 数量；
- 对每个排列使用官方 `_process_market` 在当前 observation 上执行，保留每个订单的实际成交数量。

评分不能只看无对手时的现金。至少包括：无对手基线、可见路线同序 SELL 压力、逆序 SELL 压力、单商品集中压力和大批量压力。未知对手情景只用于下行保护，不当作真实对手存在的证据。

候选只有在所有压力情景中满足以下条件才可被接受：

- 每种 baseline 必须购买/雇工/卖出的实际成交数量不减少；
- 不增加仓库溢出，不减少 baseline 的单位任务交付；
- 多个压力情景的现金或可兑现库存严格改善，且无一个情景明显下降；
- 订单数量、形状和运行时间仍在限制内。

## 为什么必须联合评估

只改市场排序会遇到库存尚未回仓、现金不足和订单索引屏障；只改移动又可能让某个高价值商品无法在本回合成交。规划器应先模拟单位动作得到 post-unit shed，再在这个状态上做市场排序，最后把排序后的订单与单位动作一起通过一回合官方内核。不能用“请求数量”代替实际成交，也不能将固定对手录像替换进未来状态。

## 已完成的机制探针

在 5 场真实负局上，固定线上双方的 pre-action 状态和双方实际动作，只枚举我方当前回合订单排列，发现 133 个当前回合正向机会；其中 33 个单回合增益至少 100。最常见的是：

- BUY_SEED WHEAT → BUY_PRODUCT WHEAT 改为先买商品；
- SELL → BUY_ANIMAL 改为先完成动物购买；
- SELL → BUY_PRODUCT 改为先买商品。

这个统计是结算机制诊断，不是整局反事实收益；不能把 133 个局部增益相加成线上预测。它只说明固定 SELL→BUY 排序确实会错过机会，且机会出现在 BUY/HIRE 屏障附近，正好超出 v3 的 SELL-only 搜索范围。

## 验证顺序

1. 先用官方内核对单 callback 的 order permutation 做单元测试，逐订单核对现金、库存和成交数量。
2. 再用真实 replay observation 做描述性 oracle，记录机会频率、订单类型、当前库存和现金余量；不改变未来状态。
3. 实现只改订单顺序的候选，使用完整真实对手 agent，在 V46、Reactive7、Pipe8、一个异构旧路线和线上开局组合上测试。
4. 每个候选至少使用 8 个新 seed、双 seat；seed 是统计簇。主要指标为 point、W/T/L、margin 和产量/溢出诊断，cash 只作为解释变量。
5. 只有在订单层通过后，才开启一个单位、一个短窗口的全局任务分配；任何新 worker 路线若出现 baseline 任务损失、库存溢出、雇工短缺或运行时间超限，立即拒绝。

## 当前停止线

现有 v3 线上问题已经说明 SELL-only overlay 覆盖不足，但还没有证明“所有 BUY 前移”安全。下一步应先完成官方内核一致的有限订单排序实验和真实对手验证，再考虑把路线分配接入模型。没有通过新 seed 的 paired point 检验前，不制作线上提交包。
