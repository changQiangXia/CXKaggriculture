## 提交准则（必须遵守）

1. **未经用户明确授权绝不提交。** 本地实验通过只表示候选待授权；脚本、监控和自动任务不得调用 Kaggle submit。
2. 提交前必须完成本地 paired 验证：common seeds、双 seat、多个强对手（至少 v37/Flex/Thomas/Dmitrii），720 steps、DONE、零 stderr/timeout，并检查 latency、最小 margin、5% 分位、seat 方差和负局数。
3. 一次只改一个可识别变量；固定 replay tape 只能做机制诊断，必须有交互式对手 panel 才算策略证据。
4. 上传异常先查 submissions/ref 和 active queue，禁止盲目重试消耗机会。
5. 提交后暂停继续改代码，先等待足够线上终局对局，再按对手、seat、seed、时间和分差分析。

## 新增共识：RL、高手回放与硬编码门控

这场比赛不适合把 720 步完整轨迹直接交给 PPO、DQN 或 self-play 去端到端优化。主要原因是终局奖励稀疏、信用分配跨度长、双方共享市场造成环境非平稳、对手策略和 matchmaking 会变化、private 环境可能发生 shake，而提交环境还受每步算力和延迟约束。单卡 4090 可以支持保守的离线实验，但不足以让大规模端到端 RL 的高方差结果成为可靠线上策略。

RL 不是完全禁止，而是限定为局部工具：

- 用高分 replay 做 route/profile 的 behavior cloning；
- 对少量 SELL 顺序、提前/保持销售、继续 harvest/先清库存等离散选择做短 horizon value ranking；
- 在已有的少量策略 profile 之间做阶段选择；
- 只学习关键参数或候选动作排序，不直接替换完整 V37/V42 policy。

任何局部模型都必须使用真实 engine 的反事实验证，按 seed、opening、对手族和 seat 留出 holdout；目标函数同时惩罚负局、最差 margin、5% 分位退化和 seat 方差。状态覆盖不足、账本不一致、置信度低或候选价值差距过小时，必须回退到 V37/V42。

高手录像适合做 tape mining，不适合原样复制 action tape。一条录像绑定特定 seed、seat、opening、shop 解锁、市场库存/价格、对手动作和比赛版本；共享市场中复制一次 SELL 还会改变后续价格和库存，第一处状态偏差会让后续动作逐渐失配。公开高分录像也可能来自已经变化的对手池或旧的 rating 环境。

从高手 replay 中应提取跨轨迹的不变量和策略结构：

- 开局现金与资产投入门槛；
- day-6 shop 组合到 route/profile 的映射；
- 何时解锁土地、雇工和动物；
- 不同 shed/carried 压力下的生产与清仓节奏；
- 市场库存和价格斜率下的 SELL 合并、拆分与顺序；
- day 27–29 以及 623/695 附近的终局处理；
- 对手采用不同 opening 时仍然稳定的动作。

这些规律应表达为“阶段 + 可见状态条件 → 候选 profile/动作排序”，而不是“某个 step 永远执行某人的固定动作”。录像中的策略必须先在固定 tape 上做反事实检查，再放到自适应交互式对手和未见 seed 的 paired panel；单条高手录像只能产生假设，不能作为测试标签或线上强度证明。

失败 replay 和胜局 replay 的用途不同：

- 失败 replay 用于定位脆弱机制、建立可证伪假设和设计最小干预；
- 胜局 replay 用于提炼主策略的稳定不变量、阶段 profile 和保护性门槛；
- 二者都不能单独决定全局改法，必须结合中间状态、action-level diff 和真实 engine 反事实。

硬编码门控是当前更现实的改进手段，但门控必须是状态驱动且局部的：

- 只使用当时 observation 可见的状态；
- 绑定 opening、day-6、day 12/18、day 27–29、623/695 等明确阶段边界；
- 联合检查现金、shed、worker carried、市场价格/库存、未来 SELL/PICKUP/BUY barrier、订单槽和 sale debt；
- 具有 telemetry、kill switch、状态契约和父动作回退；
- 低置信度或分布外状态直接沿用 V37/V42；
- 每次只改变一个可识别变量，并同时保留 no-op 和 parent-layer ablation。

禁止把单一条件变成全局抑制规则，例如“shed 高就停止所有 harvest”“看到杂草就禁用输入 planner”或“某商品价格低就提前卖完”。过去 weedguard、surplus、late-sale、全局容量和简单 quote-floor 实验的退化，说明主策略的 opening、route、生产、容量、销售 debt 和终局清仓是一个耦合闭环，孤立修改单一动作很容易牵一发动全身。

优先级因此确定为：先建立高手 replay 的阶段/市场/库存索引，提炼 profile 不变量；再研究已有明确因果线索的 step-648 SELL merge/order；随后做 day 27–29 的市场流量与真实物理库存联合决策，以及 623/695 的 72-step 容量/劳动模拟。只有完整 paired panel 证明无尾部退化，候选才可进入“待用户授权提交”。

## 监控脚本的使用边界与按需策略

监控脚本不是比赛运行、模型推理或提交流程的硬依赖。Kaggle 会保留已创建的 episode、replay 和 logs；只要保存 submission ID 和 episode ID，之后仍可以按需查询。因此不需要让 daemon 永久常驻。

脚本当前的作用是：查询 active queue 的两个 submission、发现新 episode、下载尚未记录的 replay、对 loss/tie 下载双方 logs，并维护 `state.json`。它只读 Kaggle，不调用 submit，也不会改变 agent 行为。

长期常驻的缺点是当前脚本需要先下载 replay 才能分类 outcome，并且会保存新发现的 win replay。动态比赛中早期胜局很快失去参考价值，daemon 长期运行会让 replay 目录重新快速膨胀。更合理的运行策略是：

- 没有新提交、没有正在观察的线上实验时，停止 daemon，只保留脚本、state、loss/tie logs 和摘要；
- 需要分析线上结果时运行一次 `python monitor_agent_logs.py --once`；
- 刚提交新 agent、等待早期对局时，才启动 600 秒轮询；
- 观察窗口结束后再次停止 daemon；
- 未来应把 win/validation 只保留摘要，loss/tie 才保留完整 replay。

常用命令：

```bash
cd /root/autodl-tmp
python monitor_agent_logs.py --once
nohup python monitor_agent_logs.py --interval 600 >> agent_monitor/monitor.log 2>&1 &
echo $! > agent_monitor/monitor.pid
```

当前脚本默认只监控 `team-submissions` 返回的两个最新 active submission。active queue 会在新提交后替换最旧项；如果 daemon 停止时间过长，旧 submission 退出 active queue 后，下一次普通 `--once` 可能不会再自动扫描它。因此停止前必须保存 submission ID、提交时间、public score、active queue 位置和收集状态。恢复历史 submission 时应使用定向 submission 扫描；当前脚本尚未提供 `--submission-id` 参数，不能随意使用 `--all-complete`，以免重新遍历并下载大量历史 replay。

当前 daemon 曾以 PID `3681` 运行；清理和交接期间已重新启动过，恢复研究时先用 `pgrep -af 'python monitor_agent_logs.py'`、`monitor.pid` 和 `state.json` heartbeat 确认是否真的在运行，避免重复实例。监控策略的默认原则是“脚本保留、daemon 按需运行、submission ID 单独登记、原始 replay 按 outcome 和新鲜度分级保存”。
