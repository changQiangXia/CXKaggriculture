# v3 线上约 2400 分的原因诊断

日期：2026-09-18

对象：`candidate_v45_q25_sellsearch_v3.tar.gz`（Kaggle submission `56303424`）。
父版本：`candidate_v45_q25.tar.gz`（submission `56287561`）。本轮只做回放、账本和基准审计，未修改模型，也未提交新包。

## 结论先行

当前证据不支持把 v3 的约 2400 分归因于压缩包、loader 或 Python 路径错误。v3 的修改只覆盖一个很窄的场景：父模型已经生成一个**纯 SELL、且含重复商品**的开头订单块时，对最多四个 SELL 订单做有限重排。它不改变工人动作、生产路线、市场购买数量、BUY/HIRE 屏障前后的顺序，也不处理大多数线上订单。

线上真正拉开差距的地方，集中在资金和市场结算链：

1. 同样需要买小麦时，BUY_SEED 与 BUY_PRODUCT 的先后会改变动态价格；v3 所继承的 Q25 路径多次把买商品放在后面，单回合多付几十到 240。
2. 现金差几十到一百时，下一次 HIRE 和 BUY_ANIMAL 的结算会造成少买一只羊，随后减少羊毛、肥料等产出和销售收入。
3. 仓库容量和销售时机处理不足会造成夜间溢出，或先卖低价值小麦、下一回合再卖高价值胡萝卜，最终同样的产量得到更低现金。

这些问题大多属于 Q25 父策略已经存在的资金、生产和兑现路径；v3 的 SELL-only overlay 没有触及它们。由于两个提交面对的线上对手池和时间不同，Q25 与 v3 的约 180–210 分评级差只能作为背景，不能当作 v3 改动造成同等幅度退化的因果证据。

## 证据层级

### 1. 上传包和线上行为

- v3 submission `56303424` 的评级快照为 `2401.0`；父 Q25 的历史快照为 `2582.0`。API 后续查询的数值会小幅变化。
- v3 archive SHA-256：`4ba0937507b352ec5c9b41b2ad8e4bc766873e0feb5703524bc6cd626d8f7395`。
- 包内 `main.py` 和工作区 v3 源码 SHA-256：`e262fe4f218effbd4bce1f0089f20e86f7698b181e0c46ba51b0e21ff8c93d9`。
- 用 Kaggle 官方 callable 从 v3 包内 `main.py` 复现六场（四场大负局、两场近平局）时，线上 719 个 callback 全部一致。对应父 Q25 五场 719/719，一场 718/719；唯一差异是 episode `110101510` callback 575 的重复 WHEAT SELL 次序。

这只能排除当前抽查样本中的明显打包/加载问题，不能把六场抽查扩大成对所有隐藏回合的绝对证明，但它不支持“v3 因包损坏而只有 2400 分”的解释。

### 2. 线上样本概况

目前保存了 58 场 v3 回放：35 胜、23 负。负局平均分差 `-646.1`，中位数 `-532`；最大四场为 `-2899`、`-1841`、`-1534`、`-1050`。负局中双方完整 action 相同的比例平均约 92%。

前 48 个 callback 的线上近镜像统计为：

- farmer/hands 单位动作相同率平均 97.38%；
- market 列表相同率平均 95.44%；
- 完整 action 相同率平均 92.85%；
- 负局的单位动作相同率 98.46%，反而高于胜局的 96.67%。

因此主要问题不是“我们的工人路线完全走错”，而是同一类路线在少数关键市场、资金和容量决策上落后。这个结论来自线上事实对比，不把对手录像的动作替换进我们的未来状态。

## 三个已核对的失分机制

对五局（共 3595 个 callback）从真实 `observation[t]` 出发，使用线上双方真实的 `steps[t+1].action`，调用官方 `_apply_unit_action` 和 `_process_market`。重算现金与下一条回放状态 0 mismatch；实际成交由 `_commit_unit` 记录，而不是把订单请求量误当成交量。

### Debmalya，episode 110065863，终局差 -2899

除 WHEAT 外，双方实际收获量完全一致；WHEAT 为 v3 587、对手 590。小麦买卖净现金 v3 为 10146，对手为 12553，单项差 `-2407`；同样售出 249 个草莓，收入又差 `-423`。其余成交贡献合计后，正好得到终局 `-2899`。

几个可复现的购买回合：

- callback 300：双方买 WHEAT 48，v3 先 BUY_SEED 再 BUY_PRODUCT，实际支付 2080；对手顺序相反，支付 2010，单回合差 70。
- callback 368：双方买 89，v3 支付 3889、对手 3656，差 233。
- callback 524：双方买 90，v3 支付 3940、对手 3700，差 240。

这说明动态市场中的订单索引和商品价格路径比 SELL 重排更早、更频繁地决定现金差。

### yukio，episode 110065738，终局差 -1841

callback 217 双方提出相同的 SELL FERTILIZER、HIRE、BUY_ANIMAL SHEEP 2。v3 当时起始现金 847，对手 965；双方各卖一单位肥料得到 81 后，v3 只成功买到 1 只羊，对手买到 2 只。

整局实际买羊为 10 对 11，羊毛产量为 239 对 261，肥料产量为 357 对 373。羊毛销售差 `-2045`，肥料销售差 `-428`；少买羊节省的 500 只是短期现金表象，不能抵消之后的生产收入。callback 406 的羊毛销售一次就出现卖 2 对卖 8，现金差恶化 1386。

这里的根因是现金缺口下的投资和结算顺序，而不是路线移动本身。

### Aura Farming，episode 110051331，终局差 -690

v3 多收 6 个 MELON，胡萝卜、牛奶和鸡蛋的实际收获量分别与对手相同（胡萝卜 133、牛奶 152、鸡蛋 147），但最终现金仍落后：

- 胡萝卜都卖 133，收入 60832 对 61843，差 `-1011`；
- 牛奶都卖 152，收入 4910 对 5241，差 `-331`；
- 鸡蛋收获都为 147，v3 只卖出 139，对手卖出 147，差 `-360`。

逐夜核对显示 v3 在 callback 503 溢出 4 蛋，在 551 溢出 2 蛋和 7 麦，在 575 溢出 2 蛋和 4 麦；对手相应夜晚没有这些丢失。callback 696 双方都有约 40 个胡萝卜，v3 先卖 36 个小麦只得 762，对手先卖 32 个胡萝卜得到 16065；v3 下一回合才卖胡萝卜。这里是容量和销售时机的兑现损失。

### 两个近平局也指向小麦市场

在 KOSUKE MATSUDA（episode `110074399`，`-28`）和 Rifqi Haikal（episode `110084132`，`-9`）中，双方所有商品产量和非小麦成交都相同，终局差完全来自 WHEAT 的买卖净现金。几十元就足以改变胜负，说明现金账本的细节会直接影响线上排名。

## 为什么本地验证没有预警

父 Q25 与 v3 的 72 行 paired evaluator（固定开发 seed 9064–9069，双 seat）中，动作确实改变 62/72 行，但胜负完全没有改变：48 行本来赢仍赢，24 行本来输仍输；point delta 为 0，现金平均只增加 5.33。这个结果只能说明 SELL overlay 在该小面板上是边际改动，不能说明它能对抗新线上对手。

更关键的是基准构成存在选择偏差：旧 Thomas、V37、Dmitri 家族在面板中抬高总体成绩，而近期 V46、Reactive7 两个压力家族合计 24 行全部输。开发 seed 只有 4/6 个独立 seed 簇，双座位共享同一市场随机过程，源码和 tar 的重跑也不能算新样本。

线上 58 局的近镜像动作并不等于本地面板已经覆盖了同一策略：线上首回合出现了 `BUY 7 → SELL 2`、`BUY 10 → SELL 10`、`BUY 5 → SELL 5` 等组合，它们会绕过 v3 只处理“纯 SELL 重复块”的触发条件。首回合分组与胜负有混杂因素，不能单独当作因果结论，但足以说明覆盖机制不对齐。

## 结论边界和后续验证条件

当前能下的稳健结论是：

- v3 没有证据显示存在上传或 loader 故障；
- SELL 重排的局部收益很小，且没有改变开发面板胜负；
- 线上主要可复现差距在动态 BUY 顺序、资金缺口下的动物/雇工投资、容量溢出和销售时机；
- 不能把约 180–210 分评级快照差直接当成 v3 overlay 的退化幅度，也不能把某一个回放的改序收益累加成整局线上提升。

如果下一轮继续研究，应先做分层的真实反应式对手面板：近期 V46/Reactive7、线上开局组合的完整 agent、一个异构旧路线，并使用至少 8 个新 seed、双 seat，以 seed 为统计簇。主要指标应是 point、W/T/L 和 margin；cash 只用于解释机制。买单跨 BUY/HIRE 屏障的任何修改，都必须在完整未来反应式对局中验证，不能用固定对手 tape 得出强度结论。
