## 1. 最影响下一步决策的发现

1. **七份 notebook 不是七个独立强模型，而是五种策略实现。** 原版 Beyond 48-0 与带“2780”前缀的版本输出完全相同的源码和归档；“2842”只把 Beyond 的开局数量从 50 改为 10；Pipe-7 只把 V45 的数量从 70 改为 5；`kaggriculture.ipynb` 的实际代码与 V45 的 AST 相同。
2. **“2842”已经披露这些优势被针对性应对。** 作者在 postscript 中报告 V46 击败了自己的 n=10 和 n=50 版本。这是本批材料最需要补入我们判断的新信息。文件夹没有 V46 源码，因此这里不能称为我们独立复现的结论。
3. **最优 opening 是对手相关的，不是单个参数的固有属性。** 作者从“25–50 是平台”修正为“阈值取决于对手的资金余量”；随后又承认自己构造的全循环矩阵不能代表线上对手群体。
4. **验证方法比特定数量更值得复用，但作者自己的方法和表述也要审查。** 90 分不是统计学上确定的噪声界限；64 个商店组合不是整个随机环境；同 seed 不保证修改策略后的商店抽样一致。
5. **Beyond 的“可执行性模拟”不是完整证明。** 实际代码没有逐商品库存约束，本次用空仓卖奶的反例证明它会误报成功。不能把其文字中的安全承诺直接复制为我们的验收依据。

## 3. 七份材料具体提供了什么

### 3.1 V44：识别相似农场，再扩大销售预留窗口

V44 原文 cell 0、11 与提取代码一致：继承 V43；观察到对手执行相似路线时，将预留窗口提高到 8；发现对方在己方入库同回合出售时，升级到 24。观察和调整绑定具体阶段及克隆识别条件。

这与“始终把 horizon 设为 24”有本质区别。V44 的一般门控不能用 Beyond 的常量覆盖来描述。

作者报告：独立 32 worlds × 9 rivals × 双席，V44 为 462/56/58，V43 为 378/116/82；配对比赛积分提升 12.50 个百分点，CI 为 [10.59, 14.41]。对 `fastclone24` 仍有退步：V43 19/45，V44 11/53，尽管现金差改善 +59。这直接说明**现金差增加不等于比赛积分增加**。本次未复跑这些对局。

V44 用固定对手动作流回放的结果也明确标注为诊断证据。用户提出的“先比较相似策略在哪个阶段拉开差距”与这一用途一致；固定录像不能成为自适应对手泛化的证明。

### 3.2 V45：改动很小，但代价已经在原文披露

cloning-agent 原文 cell 0、11：只在父策略给出标准开局时，将拆分买入替换为一次 `BUY WHEAT 70` 加一次 `SELL WHEAT 70`。完整 V44 底盘保留。

作者报告的独立面板为 620/20/0，相对于 V44 比赛积分提升 15.94 个百分点；同时公开了 Two Coins 开局族的代价，以及 `mirror_counter` 从 64 胜变成 62 胜 2 负。它从来没有证明“对任何策略都不自伤”。

尤其需要保留作者的两句限制：开局改变可能通过空地、杂草随机数消耗改变商店抽样；因此 V44 那套固定录像比较不能直接用于 V45 开局修改。

### 3.3 Pipe-7：数量消融属实，夸张标题不能扩大证据范围

实际提交源码确实只把 V45 的 70 改为 5，没有额外神秘层。原文报告了两套不同规模实验：

- 小 tournament：179 胜 1 负，99.4%。
- 9 个对手各 200 局的大面板：1,754 胜 46 负，97.4%。

这两个数字不能混用。Autoloop、Union-Find、twin graph 是作者描述的开发工具；本地这份 notebook 交付的是打包 agent，没有交付足够复现 1,800 局结论的完整 harness、逐局结果和对手冻结清单。因此应将胜率保留为作者报告。

Pipe-7 把效果解释为“买得越多，对自己价格冲击越大、往返开始亏钱”。这个解释不完整：本地引擎明确设计了未受扰动市场中的往返中性，实际优劣来自双方订单交互、可执行数量、现金和后续计划。尤其不能从对 Q70 的扫参得出 Q5 对其他 opening 最优。

### 3.4 原版 Beyond 与 2780：同一代码，研究说明有改进

“2780”不是在原版上又做了一轮策略增强。它仍是 K0006，n=50。新增价值主要是：

- 更明确地说明阈值取决于对手的资金余量；
- 补充第三个测量陷阱：构建脚本默认输出路径覆盖了已发布模型，导致标签与实际对手不符；
- 保留策略失败记录和 four-tier 验收方法。

四条规则实际执行结构为：父策略内的 horizon 覆盖；标准开局替换；提前销售；订单前置。`_Horizons.get()` 将父策略读到的 ≥4 映射为 24，2/3 阶段保留。它不是 V44 的克隆门控 8→24。

作者列举了 11 项实验，其中既有保留项、被替代项，也有负面项。“11 个失败实验”是总结中的误读。全季重复资金攻击失败的解释有价值：应研究**购买承诺是否缺少现金余量**，不能把“抬高小麦价格”本身当作目标。

### 3.5 2842：最值得读的是否定结果与 postscript

这份代码仅将 K0006 的 50 改成 10。作者描述：自建数量全循环中 n=10 没有负局，但线上 n=10 的分数比 n=50 低 24；因此承认该矩阵未必覆盖线上分布。

cell 6 的 postscript 更关键：

- 作者引述 V46 公开表：对 `pub_beyond48`，前一版本 0/64/0，V46 为 52/12/0。
- 作者另报本地 24 seeds × 双席：V46 对其 n=10 为 40–8，对 n=50 为 42–6。

这是两组不同实验，不能揉成一个胜率。文件夹没有 V46 完整源码、表格原始数据或测试日志，本次也未访问外部页面核验。所以准确结论是：**材料已经提供“已有反制”的强研究线索；旧模型的高分不能再当当前强度证明。**

### 3.6 kaggriculture：实际代码比版本故事更可靠

这篇介绍 V17 模块底盘、V18/V39、V19/V45 的经历。实际 `%%writefile` 单元是 V45 的 AST 等价代码。因此不能把故事里 V17、V18 的每个版本当作已经拥有的独立可运行基准。

总结把 R44 Mirror Counter 归到“2842”的创新并不准确：它出现在 evolution 笔记的继承层说明，并已存在于 V43/V45 父谱系代码。不要把层名 R44 与发布版本 V44 混为一谈。

## 4. 市场规则核验：精确到单位，不能只画订单轮流的箭头

本次读取了本机 `kaggriculture.py`，记录在 [engine_reference.json](engine_reference.json)。其 `_process_market` 按订单索引推进；对该索引的 BUY/SELL，**每个单位先为双方报价，再提交双方结果**，然后处理下一个单位。不是先完整执行 player 0 的订单、再给 player 1 报价。

同方向同商品的同索引单位使用相同报价。买卖方向不同时也不能笼统说“价格相同”：BUY_PRODUCT 按 `inventory - 1` 报价，SELL 按 `inventory` 报价。HIRE/BUY_LAND 走一次性处理。

由此有三个限制：

1. “每个成交单位都改变库存”并非绝对：SELL 在价格为 1 时不增加市场供给。
2. 对市场独立往返中性、对自身相对对称，不等于对任意异型对手都安全；资金和仓容约束还可能造成部分成交。
3. 不直接修改农场动作列表，也可能改变现金、采购成交、种植、空地数量和之后的随机世界。

本机 package metadata 为 1.25.9，但游戏文件 SHA-256 为 `bc8a54879ef02c7ea64b8b333d6a976f0ea65c4949149d01f463f23bccee653e`，恰与父策略内声明的 1.32.7 游戏源码哈希相同。**不能仅凭包版本不同，就断言游戏规则不同。** 这也不能反向证明当前线上运行器与整个本地环境完全一致；本轮未抓取线上源码。

终局奖励代码只取现金；库存不自动计入财富。终局规划因此有价值。但“提前收割未成熟作物”这个总结例子不符合规则：未达到 first_yield_day 的 HARVEST 是无效动作。正确表述是“对已经达到可收获年龄、但尚未达到最大产量的作物，权衡尽早收割和及时出售”。

## 5. 代码与作者安全描述之间的差距

### 5.1 frontload 检查器缺少逐商品库存

源码 [beyond50.py](beyond50.py) 的 `_simulate` 只收 `shed_total`，没有每种商品库存。遇到 SELL 就增加现金并减少仓库总数，不检验该商品是否存在，也不阻止仓库总数为负。

本次只独立执行其价格和检查函数，给定现金 0、空仓、订单 `SELL MILK 1 → BUY_PRODUCT WHEAT 1`，压力 0 和 1 两种模式都返回 `all_executed=True`、剩余现金 134。真实引擎会拒绝空仓卖奶，继而买不起小麦。结果保存在 [simulator_counterexample.json](simulator_counterexample.json)。

这证明其检查不充分，**不证明这个反例一定会出现在实际父策略轨迹，也不直接推翻作者整套胜率**。移植时必须补齐商品库存和 worker 动作后的真实状态，才能把它称为执行保证。pressure=0/1 也只是两种场景，不是任意对手订单的严格上下界。

### 5.2 advance_declined_full 的文字解释与代码不一致

原文把它解释成“提前销售不能完整执行时拒绝”。实际代码是在 `len(cur)+len(extra)>max_orders` 时截断额外订单并累加计数，主要反映**订单槽位不足**，不是商品/资金可执行性验证；且可能只是截断一部分，而非整次拒绝。

提前销售排除 WHEAT/FERTILIZER，并保护拼接未来订单流中的首个 SELL 商品，目的是保留父策略的现金抵扣和补给关系。这些约束是值得学习的部分；仅抄“提前两步卖”会丢掉关键契约。

### 5.3 非标准环境回退也不是整套改动均撤销

frontload、advance 和 opening 检查 `_standard(configuration)`；但 `_R37_HORIZONS` 的替换在加载阶段就安装了。若使用非标准配置，不能仅因外层返回父动作，就认为 horizon 已恢复父版本。这是静态代码边界，当前标准比赛下是否产生问题未在本次测试。

## 6. 对用户总结的保留与修正

| 原观点 | 本次判断与修正 |
|---|---|
| 正确测量比继续叠层更重要 | 保留。文件身份、对手实际执行、真 runner、开发集与验收集分离是具体做法 |
| 比赛本质是市场博弈，不是农业经营 | 收窄。在这些成熟且相似的生产路线之间，市场微观机制是关键差异；不能推导农业已无优化空间 |
| 同一代码两份提交差 90 分，所以 90 分以内都不是真实差距 | 修正。一对复制提交只能展示大幅评分波动，不能估计一个普遍的 90 分噪声界限；超过 90 也不自动证明增强 |
| 2842 的数字是可靠的统计阈值 | 修正。正文同时出现 2857 对 2786（差 71）和相近局数时约 2767（差约 90）；B 的 88W+26L+4T 为 118，表中却写 119 games。统计口径本身仍需原始数据澄清 |
| 128/128 worlds 是 128 个独立世界 | 修正。文中设计是 64 个首两家商店组合 × 双席 = 128 局；双席不能当独立样本翻倍 |
| 64 个世界覆盖后就能推断线上普适增强 | 修正。每个组合仅一个 seed 不覆盖组内杂草、后续商店及对手差异；且 opening 改变可能令组合标签漂移 |
| ≥64 世界、128 场、bootstrap CI 就足够 | 收窄。这是较好的验收组成，不是魔法门槛；CI 不包含缺失对手家族、多重筛选、非平稳对手池造成的偏差 |
| horizon 24、数量 5–40 是普适最优 | 修正。它们是底盘、对手、状态和市场参数条件下的经验结果 |
| 排行榜只用来检查没搞坏 | 收窄。线上成熟对局中的对手分布和败局机制仍是重要分布外证据；单个短期评分不适合选微小改动 |
| 对称且市场中性的攻击不会自伤 | 修正。V45 本人公开了异型开局导致自己少种瓜的代价 |
| 验收应要求同一代码两次提交结果相同 | 修正。确定的本地运行条件下核对复现；两份线上 submission 的随机匹配和评分无需相等 |
| 收集优秀 tape 后可直接重放验证 | 保留用户此前限制：用于观察阶段和机制；策略变化后必须重新做真实交互，不能把固定对手流当强度证据 |

“全局范式”应写成：**在保全生产、供给、资金和执行契约的条件下，通过公开状态判断某类市场干预是否有机会改善比赛结果，并以未见世界、未见对手族和线上机制证据验收。** 它不能缩写成“少买麦”或“更早卖”。

## 7. 这次材料核对也纠正了我之前的两个判断

第一，我之前强调“本地 1.25.9 对线上 1.32.7”的版本差；本次直接核对游戏文件哈希后，不能继续把包版本号当作规则差异证据。应分别固定游戏源码和运行器，而不是只报一个包版本。

第二，刚才 `adaptive_q20_x*` 实验把 step 1 的 `SELL 13 + BUY 5` 替换为等量 BUY/SELL，取消了原先的净小麦补给。Q20 step 0 正常完整往返后没有留下这 5 单位饲料。这个改动首先违反了补给契约。我此前把其巨大退化概括为“库存门控过拟合”，归因不充分；它不能用来否定整个状态门控方向。这里仅更正解释，不继续修补或扩展实验。

另外，旧的 `candidate_v45_q20_step1_buy*` 代码受 `_OPEN_FEED_STEP1 < 5` 约束，而常量为 5。其 step 1 修改分支不会触发；这类不变化的面板不能当成修改通过的证据。今后的实验身份核验必须包含“分支确实触发、实际动作确实不同”。

## 8. 给下一个 goal 留下的输入，而非本轮继续执行的任务

如果后续重新开始候选构建，优先顺序应当是：

1. 冻结这五种策略及实际提交包身份；分别标记参数家族与独立底盘，避免重复加权。
2. 先核验 V46 这条新增反制线索及后续公开策略，再决定当前需要击败的参照。现有文件夹无法支持“仍然击败 V45 就接近当前前排”的假设。
3. 验证按“开发 seed → 未见 seed → 未见对手谱系”分开；商店组合作覆盖描述，同 seed 的策略比较允许结果世界分叉，并记录这种分叉。
4. 冻结前使用实际打包单文件、正确导出的最后 callable、真实 runner；记录双方 hash、实际动作、分支触发、终局钱、DONE、错误、耗时和供给账本。
5. 主指标用配对比赛积分（W=1/T=0.5/L=0），同时报告 W→L、T→W、现金差和负尾。按 seed/world 聚类 bootstrap，并对对手族分别报告。不能把同 seed 的双席当两份独立信息。
6. 区分真实鲁棒改进与针对旧 opening 的局部收益；当前线上历史最高 rating 受时间和匹配影响，单个数字不能给出可靠的“超过概率”。
