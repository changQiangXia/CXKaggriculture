# D16 计划生成器（设计稿 v1，2026-09-30 17:40 北京）

**目标**：孵化一个能在**保持状态自洽**的前提下给农场"加产能"的候选——
补上强敌多出来的那一份结构（第 4 象限 / 多一个 coop+鹅 / 更多奶牛），
从"价值密度"这个唯一被量化的缺口上再拿一档。

---

## 1. 为什么必须走这条路（今天所有捷径都被证伪）

| 捷径 | 结果 |
|---|---|
| 加雇工（+1 峰值） | 旧池 −4；新底座复查 `k_h800` −10 |
| cowswap（牛→鹅）放宽 | 惰性/负；`cw_always` 自博弈 3-5 负 |
| 羊→鹅换算子 | 0 翻转，margin −6,796；新底座自博弈 14/16 平（工具陷阱修正后未复测） |
| **羊→牛（窗口内）** | 换算子触发但**牛不落地**（动物 17→10），单局 102.7k vs **69.4k** |
| **羊→牛（全局物种替换）** | 结构成功（14 牛 0 羊、全部落地），但把饲料/销售经济打崩：117k vs **29.4k** |
| 第 4 象限扩张（V219） | 闸门放松后惰性/负（−3 / 0） |
| 番茄层阈值 | 惰性（2 局变化、0 翻转） |
| 外来 tape 片段 | 灾难（0-56 胜 / 242）——状态不兼容 |

**共同死因**：我们的执行体是 41 条**预编排的 720 步计划**，
"动物种类 / 地块用途 / 劳动力分配"三者互相咬合；任何单点改动都会让
建造-搬运-放置链、饲料预算与销售节奏失去自洽。

**唯一出路**：要么**生成**一份自洽的新计划，要么带**状态修复**地**拼接**外来片段。

## 2. 三条技术路线

### 路线 A（首选）· 伴随式状态机：不重写 tape，而是"在旁边完成一件整活"

**核心思想**：不去改 tape 的文本，而是让一个新模块在**不影响 tape 的前提下**，
用一整段连续动作完成"多一个 coop+鹅"或"多一块 4 象限地"的整活。

**可行性依据（今天的新发现）**：
* 我们的计划里**每个 coop 在稳态都是满的**（coop 2.40 / 鹅 2.40），
  但在 d14 前后存在**短暂的 0.88 个空 coop**——说明建造与放置之间有时序空隙；
* tape 的**未使用单位**是可以被识别出来的：扫描未来 N 步的 tape，
  找出既没有命令、又靠近棚屋/目标地块的单位；
* tape 对**地块**的占用同样可扫描：未来 N 步没有 PLANT/WATER/HARVEST 的地块即可作为目标。

**实现草图**：

```
触发（d10-16 任一 tick）：
  cash ≥ 3000
  geese ≤ 4
  存在空闲地块 T（未来 48 步 tape 不触碰）且我方可建（已解锁）
  存在空闲单位 U（未来 12 步 tape 全 PASS，且距 T ≤ 8 步）
行动（状态机，逐步执行，每步只覆盖 U 的命令）：
  1) U 走到 T → DIG（若 T 有作物）
  2) U → BUILD_COOP
  3) 市场加 BUY_ANIMAL GOOSE 1（若订单槽 <10）
  4) U → 走到棚屋 → PICKUP GOOSE 1
  5) U → 走回 T → PLACE GOOSE
  6) 之后交给 tape（tape 会照常喂食/照料/收集）
```

**风险控制**：
* 任一步失败（地块被占、单位被调用、现金不足）→ **整活放弃**，并把 U 与 T 的控制权交还 tape；
* 全程记录 telemetry（durable 状态机，允许中断与恢复）；
* 只在**自博弈**里先验证（20 局），再进磁带面板。

**预期收益**：+1 鹅 ≈ 1 蛋/天 × 50 ≈ 1.2-1.5k/局（后 18 天）；若能同时加奶牛则更多。

### 路线 B · 声明式计划生成器（更彻底、更慢）

把计划抽象成声明：`{动物配比, 作物配比, 每日劳动配额}`，
用**调度器**生成 720 步动作（单位-动作分配 + 移动路径 + 市场节奏），
用 byte-exact 模拟器做**闭环校验**（feed 预算、浇水覆盖、棚屋容量）。

* 优点：能做真正的结构搜索（例如把奶牛从 6 提到 10-14）；
* 缺点：等于重写执行体，工程量 1-2 天；今天不做。

### 路线 C · 外来片段 + 状态修复（D2）

把强敌 tape 的**窗口片段**平移进我们的时间线，并在边界做"状态修复"：
对齐单位位置、随身货物、未完成的浇水/收获义务。

* 今天的 D4-lite 失败（0-56 胜）证明**没有修复层就不行**；
* 修复层需要"片段对状态的假设"可解——建议先做**离线检查器**：
  给定片段与我们的当前状态，检测"不可满足的前置"（动物不在手边、地块被占等），
  只在完全可满足时才切换。
* 工程量：中高（1 天）。

## 4. 必须遵守的工具纪律（今天踩过的坑）

1. **runner 取"按插入顺序最后一个 callable"**：追加层必须把父体放进**不可调用容器**
   （`_X = {'parent': agent}`），否则父体会成为入口、层被静默绕过；
2. 磁带面板用 `mod.__dict__["agent"]`，与 runner 的口径**不同**——两边都要测；
3. 自博弈**必须换种子块**（今天遇到过 30-10 → 19-21 的种子异质）；
4. 所有结论写进 `STRUCTURAL_DIRECTIONS_20260930.md` 的修正记录，避免重踩。

## 6. 路线 A 原型实测（2026-09-30 17:30-18:40 北京）

**实现**：`georgy_arena/arms/ssm_goose{,2,3}` —— 伴随式状态机（选空闲单位 + 空闲地块，
自己完成"买鹅 → 挖/建栏 → 取鹅 → 放鹅"）。

**可行性扫描（30 局线上回放）**：

* **50% 的局存在可用窗口**（≥1 个空闲单位 + ≥1 块 48 步内不被触碰的地块，距离 ≤8）；
* 典型窗口：t≈230（d9-10，空闲地块 39-43、空闲单位 1、距离 2）或 t≈452（d18，空闲地块 21、单位 2、距离 1）。

**原型结果（自博弈，单局解剖）**：

| 版本 | 结果 |
|---|---|
| v1（先建栏后买鹅） | 造出 **5 个额外 coop**，但**鹅没买到**（订单槽被 tape 占满）→ 白挖 5 块地，比分 88,992 vs 99,314 |
| v2（先买鹅再造栏 + 逐步重试） | 仍被订单槽卡住（1 run / 0 done / 1 abort） |
| v3（踢掉最低价值卖单腾槽） | 买单**确实发出过一次**（t=283，余额 13,257），但**搬运/放置相位未接上**，最终仍只多出 coop、没有鹅 |

**结论**：路线 A 的**可行性已被证明**（窗口存在、coop 能造、买单能发），
但要在**订单槽 10 条上限 + tape 相位 + 单位/地块时序**三重耦合下把整活走完，
还需要：① 订单槽的显式预算调度；② 相位与 tape 的对齐器（谁在什么时候可以被打断）；
③ 失败回滚（把已挖地块恢复或改种）。**建议按 §3 的时间盒重新开工，不要在短线里硬塞。**

## 7. 当晚续推（21:00-22:30 北京）——把整活走通了，但发现"维护缺口"

**逐项排掉的 bug**

1. `load_agent` 取"按插入顺序最后的 callable"→ 包装层必须放在不可调用容器里（已修）；
2. 现金门 1500 太严（d9 实际只有 567-897）→ 降到 500；
3. **订单槽**：tape 的 market 列表已满 10 条 → 先截断到 9 条再追加 `BUY_ANIMAL GOOSE`；
4. **日界（t=288）手被重置**导致"单位编号"失配 → 改成**无状态选单位**（每步从 tape 为 PASS
   的单位里挑离目标最近的那个）；超时上限放宽到 200 步；
5. **到终态时提前 return** 导致 `PLACE` 母令被吞 → 先发动作再结算状态。

**结果（自博弈 seed 1500，逐 tile 追踪）**

| 时刻 | 我方(A) | 改造体(B) |
|---|---|---|
| t=310 | coops=[(4,0)EMPTY] | coops=[(4,0)EMPTY, **(0,7)EMPTY**] |
| t=545-551 | — | **PICKUP + PLACE GOOSE 成功** |
| **t=560** | coops=[] | **coops=[(3,0)OCC], geese=1** ✅ |
| t=600 | coops=[] | goose **消失**（coops 空、geese=0） |

**⇒ 最后一公里的真问题：维护缺口。** tape 的喂食/照料只覆盖它自己计划里的动物；
我们额外放的鹅**没人喂**，第二天就饿死/逃离——300 金币 + 一个 coop + 一次搬运全部报废。

**下一步（明天开工，约 1-1.5h）**
1. 状态机延长一个"**宠物维护**"阶段：每天检查我们新增的那只鹅（记录 tile），
   若 `fed_today=false` 且有小麦 → 派一个空闲单位去 `FEED`（并顺带 `CARE`/`COLLECT_FERTILIZER`）；
2. 用**自博弈 20 局**验证：动物数 +1 能否稳定保持到 d29，且胜率 ≥50%；
3. 过磁带面板（newest 242）与守卫池；通过后打包。

**这一步做完，才是"多发一只鹅"的完整闭环**；也解释了为什么所有"加法类"改动在过去都失败——
**不是加不进去，而是加了没人管**。

## 8. 维护层实测（2026-09-30 18:00-18:30 北京）——路线 A 被"零闲置劳动力"卡死

**实现**：`georgy_arena/arms/ssm_maint_layer.py`（v2）+ `ssm_goose8/main.py`（ssm7 + 维护层）。
维护层登记 PLACE GOOSE 的格子（48 步宽限覆盖 PLACE→鹅出现的延迟），每步给未喂的鹅分配
"tape PASS + 当前动作 PASS"的单位：携麦者直接 FEED；否则去棚屋 PICKUP WHEAT 1 再 FEED；
支持多鹅；并绑定同一单位（忙则等、闲则续走）。

**seed 1500 实测（vs w2_120）**

* ssm7 三次放置成功（t=345 / 551 / 575，3 个 coop 落地）；
* 维护层：`starts=3, feeds=0, pickups=1, aborts=3` —— 鹅全部饿死（d23-24 存活、d25 消失）；
* 逐步日志（d22-24）：绝大多数步 `free=0`（tape 把 12 个工人排满），只有 2 个瞬间
  出现 1-3 个空闲单位；绑定的单位随后被 tape 叫走，续走不了；棚屋小麦被 tape 卖到 0
  （38→0，反复出现）；
* margin：基线 79,624 vs 改造体 74,300（**−5,324**）。

**机制结论**

1. hands 每天日界清零，由 market 里的 `["HIRE"]×N` 重新雇佣（t=288 hands=0，t=289 hires=9）；
   任何"新增劳动力"都必须是每日重复的 HIRE（市场槽 10 条，tape 已占 9 条）；
2. tape 没有可持续的闲置劳动力：要么偷工人（打乱排程，番茄/萝卜实证为负），
   要么每天多雇一个专属工人（工资需要鹅的产出覆盖，边际大概率不划算）；
3. ⇒ 路线 A 的伴随式状态机只能完成**一次性放置**，无法完成**每日维护**；
   D16 必须走路线 B（把照护编进 720 步计划的新生成器）或 C（带状态修复的片段拼接）。

**结论**：今晚（提交窗口 22:00 前）D16 无法产出可验证候选；建议收官，
把 ssm_goose8 与维护层留作路线 B 的输入（照护相位、HIRE 预算、单位-地块账目）。

## 9. 维护层 v3 与经济学判决（2026-09-30 19:00-20:00 北京）

**技术突破（维护不再是问题）**

* 新雇的手每天在 hour 1 由 tape 雇、我们从 **hour 2**（市场此时为空）补一条 `HIRE`，
  专属手总是排在最后，不会错位 tape 的工人索引（hour 0 雇人会把手插到最前面，
  整条 tape 的 hand 指令全部错位——这是上一轮 −5k~−24k 的真正元凶）；
* 只登记 **ssm 自己放的那一只鹅**（用 `_SSM.report.done` 计数识别，避免把 tape 自带的鹅
  也纳入维护），取消买麦兜底（鹅可扛 1 天，等棚屋有麦再取）；
* 结果：`ssm_goose9` 在 seed 1500-1503 上鹅 d22-24 放下后 **活到 d28**，
  `feeds=4-6, cares=4-6, buys=0`，维护闭环成立。

**经济学判决：仍然全面为负**

* 加鹅版（ssm_goose9，单鹅 + 专属手）vs w2_120，seeds 1500-1503：
  margin **−5,191 / −23,469 / −4,032 / −3,951**；
* 纯照护版（`care_layer.py`：只雇专属手喂/照料 tape 自己的动物，零放置、零买鹅、零市场手术）：
  16 局 **0-16**，median **−3,001**，`feeds=0, cares=0` —— tape 自己已经把动物喂/照料好了，
  专属手无事可做，**30 天 × 高段位手价 ≈ −3k 全是净亏**；
* 成本结构：10-12 号工人的日价远高于 1-9 号（探针：1 手 1 金、3 手 4 金、9 手 88 金；
  高段位边际手 ≈100/天），单鹅 7-8 天产出 ≈500 金，覆盖不了手价 + 放置手术
  （丢卖单、占地块、调工人）的 2-5k。

**最终结论**：路线 A（伴随式状态机）在**技术**上已走通（放置 + 每日维护），
但在**经济**上不成立——任何"外挂劳动力/市场槽/地块"的占用都比鹅的产出贵。
照护与增量必须**替换计划内既有劳动**（路线 B 的计划生成器），
而不是在计划外新增。D16 路线 A 正式关闭。

## 10. 路线 B-lite 实测（2026-09-30 20:20-20:50 北京）——专职工人同样为负

**实现**：`georgy_arena/arms/work_layer.py`（w2_120 + 每天 hour 2 零代价 HIRE 一个专属手，
给它一份固定工作清单：喂未喂的动物 → 收 `fertilizer_available` 的化肥 → 收成熟作物
→ CARE 未照料的动物 → 浇未浇水的地；背包 ≥8 件时去棚屋 DROP）。

**16 局 vs w2_120**：**0W-16L**，mean **−8,765**，median **−7,148**；
worker 实际很忙（16 局合计 feeds 1,084 / fertilizer 1,070 / harvest 1,106 ≈ 68/67/69 每局），
但 `drops=0`，且比"纯雇佣不干活"的 −3,001 更差。

**解释**：这只手抢在 tape 之前收割/取肥/喂食，破坏了 tape 的既定收获-销售相位；
它的产出又没有进入 tape 的卖单链条（drops=0），于是纯粹是干扰 + 工资。
tape 已经处在自己的局部最优：**任何计划外新增的通用工人都具有破坏性**。

**D16 最终判决**：外挂型方案（加鹅、纯照护手、专职工人）全部为负；
增量只能通过**重写 720 步计划本身**（把新增产能替换进既有劳动配额）来实现。
这是一项 1-2 天的工程，今晚无法产出可验证候选。
