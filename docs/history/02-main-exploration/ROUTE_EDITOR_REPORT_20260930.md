# Tape 路线编辑器工作报告（2026-09-30）

## 1. 工具链（已建成并验证）

* **`route_editor.py`**：解码 `_R108_DATA`（3982 动作池 + 41 路线 id 表）→ 编辑 →
  base85/zlib 重编码写回；`Compiled` API（intern / set_action / clone_route）；
  `info` / `roundtrip` / `dump` 三个 CLI。
  **无损验证**：无修改重编码版与基线 **168/168 局逐位相同**。
* **`mk_route_edit.py`**：编辑 DSL——`--flip-crop`（作物翻转，含种子单）、
  `--pre-sell` / `--move-sells`（卖单前移/移动）、`--cap-sells`（卖单上限）、
  `--thin-hires` / `--dup-hires`（雇工密度）、`--route <id|all>`（单路线/全路线）。
* **`route_random_search.py`**：随机编辑搜索（市场单抖动 / HIRE 增减 / 作物翻转），
  批量生成变体 → 自动跑面板 → 排行。

## 2. 关键机制发现

1. **router 按阶段切换路线**：一局内依次使用 **route 0（day0-5，144 步）→
   中段路线（day6-26，504 步）→ route 2（day27-29，71 步）**；中段路线随
   "前两商店组合"变化（实测出现 9 / 105 / 107 / 111 / 112…）。
   ⇒ **编辑必须落在活跃路线**（此前 E1/E2/E4 的"零效果"全因此）；
   跨世界生效用 `--route all`。
2. **编辑生效验证**：E5（route 9 作物翻转）与基线运行时 **diff = 88 步**——
   编辑器首次真实改变了行为。
3. **库存节奏**：日初收获 → h01/h02 即清货；h20/h21 的卖单多数时候无货可卖
   （解释了"抢卖"类编辑零效果）。

## 6. 追记（2026-09-30 晚）：按中段路线的分组胜率 + E13 精修实验

对池子 168 局做了"每局实际中段路线"的普查（`route_usage_census.py`），并按路线分组：

| route | n | W/L | win% | meanMargin |
|---|---:|---|---:|---:|
| **105** | **59** | 35/24 | **59.3%** | +2,077 |
| 9 | 33 | 23/10 | 69.7% | +12,130 |
| 107 | 20 | 14/6 | 70.0% | +5,996 |
| 104 | 9 | 4/5 | 44.4% | −1,374 |
| 103 | 7 | 6/1 | 85.7% | +3,645 |
| 其余 | 40 | — | 50~100% | — |

* 结论：**最大组（105，59 局）胜率明显偏低**（59.3% vs 9/107 的 ~70%）。
* E12a（全部统一 9）−49 胜说明"无差别替换"有害；**E13 批做精细化验证**：
  * e13a：只把 route 105 的中段换成 route 9 的（影响 105 组 59 局）；
  * e13b：只把 route 105 的中段换成 route 107 的；
  * e13c：把 route 9 的中段换成 107 的（对照组）。
* 判定逻辑：若 e13a/e13b 提升 ⇒ 105 组是"路线问题"（可换路线提升胜场）；
  若变差/持平 ⇒ 105 组是"世界问题"（该商店组合天生难打）。

### E13 实测与根因（终局）

| 变体 | 结果 |
|---|---|
| e13a（105 中段 ← 9） | **84/84（−21 胜）** |
| e13b（105 中段 ← 107） | 105/63（0 翻转） |
| e13c（9 中段 ← 107） | 102/66（−3 胜） |

**根因**：对比路线原始数据——**route 105 与 107 的中段只有 7/504 步不同（近亲），
而 105 与 9、9 与 107 全 504 步不同**。即：

* 用**几乎同一份中段**的两组世界（105 组 59.3% vs 107 组 70.0%）胜率差 **10.7pp**
  ⇒ **低胜率来自"世界（商店组合）固有难度"，不是路线选择失误**；
* 换更强的 route 9 中段反而 −21 胜（e13a）⇒ "按世界定制"确实是最优；
* ⇒ **路线/路由层面的优化空间 = 0**（在现有 41 条 tape 集合内）。

**终局结论**：tape 编辑、随机搜索、片段拼接、路由精修全部为零/负；
改进只剩两条路——(a) 层（运行时硬实力）；(b) 从零生成新的中段 tape（巨大工程）。
